## 一、职业目标（对应「职业目标」20 分）

### 目标岗位
**AI 应用研发工程师（大模型应用 / Agent 方向）** · 广州 / 深圳 · 2028 届本科。

### 行业调研结论（提炼自 `docs/岗位调研表.md`）

- **7 份真实 JD 拆解**：应用岗本科即可投、算法岗普遍要求硕士 → **主攻应用岗是理性选择**（不是拍脑袋，是拆了 7 份 JD 得出的结论）。
- **冲 / 稳 / 保结构**：
  - 冲：阿里巴巴（AI 应用研发）、字节跳动（算法，作"研究过"的证据）
  - 稳：CVTE（应用开发）、金山办公（产品经理 AI 专项）、唯品会（LLM 算法）
  - 保：本地教育科技
- **3 个行业数据点**（佐证"为什么是现在"）：
  1. 2026 春招 AI 岗位量同比 **+12 倍**，占比 2.29% → 26.23%（脉脉）
  2. AI 应用开发岗占 AI 岗位 **60.97%**，最热招是 Agent 开发工程师（脉脉）—— 直接支撑"应用岗"定位
  3. 中国 AI Agent 活跃智能体 **200 万 → 500 万**，+145%（IDC）
- **核心技能要求**（JD 高频词）：Python、Prompt 工程、大模型 API、LangChain、RAG、工具调用/Function Calling、Git。

**答辩一句话**：*"我拆了 7 份真实 JD，发现应用岗占 AI 岗位六成、本科就能投，而算法岗普遍要硕士——所以我把目标定在 AI 应用开发，并针对性地补全了 JD 要求的每项技能。"*

## 二、岗位胜任力（对应「岗位胜任力」80 分）

### 2.1 专业技能（从「职镜」项目提取）

| 能力 | 具体体现 | 对应技术 |
|---|---|---|
| **RAG** | 向量召回（BGE）+ CrossEncoder 重排 + 关键词 fallback | sentence-transformers、ChromaDB |
| **Agent** | Plan-Act-Reflect 多轮智能体（规划→执行→反思，最多 3 轮） | LangGraph |
| **评测体系** | 自建 30 样本 Gold Set，MAE/RMSE/Spearman 指标 | 自研 eval 脚本 |
| **工程化** | Docker + GitHub Actions CI + pytest（覆盖率 63%）+ ruff | 完整交付 |
| **大模型应用** | Function Calling、LLM-as-Judge 质量门控、按 JD 简历优化 | OpenAI SDK |

### 2.2 综合素质

- **逻辑思维**：独立设计四维度评分公式（技能 40 + 项目 35 + 教育 15 + 软技能 10 = 100），以及 Agent 状态机的节点/条件边。
- **解决实际问题**：独立定位并修复 3 个真实 bug——
  1. PDF 上传被浏览器按 MIME 拒绝（改显式传 MIME）
  2. 专业被误识别为学校名（词表歧义）
  3. 图片 OCR 的 subprocess 中文路径编码问题（换不含中文路径 + 去引号）
- **业务理解**：从大学生「盲投、看不出差距」的求职痛点出发设计产品，用真实 JD 反推能力图谱。
- **自驱 / 动手**：独立全栈开发 + 部署 Streamlit Cloud 线上 + 拉 6 位同学真实试用。

### 2.3 实证数据（数据证明，全部可复现）

| 指标 | 结果 |
|---|---|
| 匹配器（30 样本） | **MAE 10.97**，**Spearman ρ 0.959**（秩相关接近 1，排序一致性极强） |
| 缺口召回率 | **1.0**（标注的缺口 100% 被正确识别） |
| 解析引擎 A/B | 规则 MAE 10.97 / 0.1ms vs LLM MAE 8.00 / ~1s（LLM 更准，慢 4 个数量级 → 引出混合路由） |
| 质量门控 A/B | 无门控 avg **2.91** → 有门控 avg **3.56**（重试率 70%、降级率 30%） |
| 测试覆盖率 | **63%** |

**答辩一句话**：*"我不仅做了功能，还建了评测集去量化它——匹配器 MAE 10.97、秩相关 0.959，LLM 解析比规则更准但慢一千倍，所以我才做混合路由在两者之间权衡。"*

## 三、发展潜力（对应「发展潜力」10 分）

- **持续学习**：为参赛从零自学 Streamlit、LangChain、RAG、Function Calling、LangGraph，跑通全栈。
- **创新精神（两个例子）**：
  1. **混合解析策略**——用 A/B 评测证明"规则快、LLM 准"，再设计"规则优先 + LLM 兜底"的路由，兼顾速度与准确率。
  2. **LLM-as-Judge 质量门控**——主动引入"生成 → 评审 → 重试 → 兜底"的闭环，用评测证明门控把建议质量从 2.91 提到 3.56。
- **性能与成本权衡（工程思维）**：识别出"问'我适合投哪个岗'时，Agent 会对 7 个岗位各调一次 diagnose"的调用模式问题，主动记录为「批量诊断」优化项（见 `zhijing/CLAUDE.md` 的 Future Work）——说明有成本/延迟意识，而不只是"功能跑通"。
- **应对不确定性**：无 API Key 也能完整跑通（离线降级）、向量检索不可用自动回退关键词、LLM 抽取失败静默回退规则——层层兜底，保证可交付。

**答辩一句话**：*"我能用数据发现'规则快、LLM 准'的取舍，也能发现'7 次单点调用该合并成 1 次批量'的成本问题——这是比'功能跑通'更进一步的工程判断。"*
